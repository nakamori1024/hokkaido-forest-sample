# 設計の理由

[spec.md](spec.md)（データ仕様）の各決定について、理由と、検討したほかの案をまとめる。章立ては spec.md に合わせている。

各項目は次の形で書く。

- **決定**：何に決めたか
- **理由**：そう決めた理由
- **検討したほかの案**：採らなかった案と、その理由

参照する Portolan の仕様は v0.2.0（<https://github.com/portolan-sdi/portolan-spec>）。`core.md`・`formats.md` はその中の文書を指す。

## 1. 目的と範囲

### 対象のデータ

**決定**：北海道「森林計画関係資料オープンデータ」のうち、「林小班区画及び森林資源データ」（小班・林班の shp、調査簿 xlsx、コード表 xlsx）だけを対象にする。

**理由**

- 論点を、区画と属性の扱いに絞れる
- ほかのデータ（集計表の xlsm など）は、整形など本質的でない作業が多い

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 同じページの 5 種類（林小班区画及び森林資源データ、kmz、QField 用、森林資源構成表、齢級別伐採量）をすべて扱う | 集計表の整形など、本質的でない作業が多い。集計表は、必要になれば Portolan の表データの collection として後から足せる |

### 配る形式

**決定**：Shapefile と Excel は配らない。データ本体は GeoParquet（形状あり）と Parquet（表データ）、表示用は PMTiles にする。

**理由**

- Portolan が求める形式（GeoParquet、PMTiles、STAC）に合わせる
- 元のコード表の xlsx は印刷用の段組みで、機械で読むには手で整形する必要がある。Parquet にすれば機械で読める

### 非公式のコピーとして作る

**決定**：北海道ではない個人がホストする mirror（非公式コピー）として作る。Portolan の Source Provenance（core.md）に従い、`via` リンク・`updated`・`source` アセットを持つ。

**理由**

- 北海道がこのデータを Portolan の形で公開することはないので、official（作成者とホストが同じ）の場合を書く必要がない
- core.md では、作成者（北海道）とホストが違うカタログは mirror になる。mirror には、元のページへの `via` リンク（type `text/html`）と、各カタログ・collection の `updated`（最後に元データと同期した日時、RFC 3339）が MUST、元のファイルを指す `source` アセットが SHOULD
- 元が STAC を公開していれば `canonical` リンクが MUST だが、道は STAC を公開していない

## 2. 元データ

### コード名称の出典

**決定**：codes の名称・略称は、道の「森林調査簿コード表」PDF（<https://www.pref.hokkaido.lg.jp/sr/srk/97786.html> に掲載、69 項目）を出典にする。

**理由**

- zip の中の `森林調査簿コード.xlsx` は、この PDF の抜粋で、調査簿で使われているコードが載っていない
  - 樹種コード 72〜90 の 17 種類
  - 混植サイン 2・3（xlsx は 0・1 だけ）
  - 疎密度・立地距離・指定施業要件・特定保安林区分は、区分自体がない
- PDF には、これらの定義がすべてある。調査簿で使われているコードは、すべて PDF に載っている

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| zip の中の xlsx を出典にする | 抜粋で、調査簿のコードの一部が載っていない |

## 3. カタログの構成

### 年のサブカタログ

**決定**：構成は「年（サブカタログ）> 小班・林班など（collection）」にする。

**理由**

- 年をまたいで比べる使い方（研究など）はありうる。年ごとの同じ名前のファイルは、glob（例：`read_parquet('*/subcompartments/subcompartments.parquet')`）でまとめて読める
- PMTiles のリンクとスタイルは collection 単位で持つ決まりなので、年ごとに collection を分けるとタイルも年ごとに分けられる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 振興局 > 年 > 小班・林班 | 次の「振興局で分けない」 |
| 小班・林班の collection の中に、年ごとの item を並べる | PMTiles のリンクとスタイルは collection 単位で持つので、年ごとにタイルを分けにくい |

### 振興局で分けない

**決定**：振興局は階層に入れない。全道を 1 つのファイルにし、振興局はコードの列で持つ。

**理由**

- 振興局をまたいで見る場面（境界付近）はあまり多くないが、全道を分析するには 14 ファイルの結合が要り、境界付近ではファイルをまたぐ
- GeoParquet を空間順に並べ、行グループごとの bbox の統計を持てば、範囲を絞った読み込みはファイルの中で効く
- 全道で 1 ファイルにしても、令和6年末で小班 880,834 地物・約 210 MB、林班 19,814 地物・約 30 MB（EPSG:4612、zstd）で、分割の目安（2 GB）を大きく下回る

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 振興局 > 年 > 小班・林班 | 元データの配り方と対応し移行しやすいが、上の理由で不便。配信の都合（容量を抑えるための分割）が ID に残る |
| partition 拡張で振興局ごとに分割する | 容量が目安を超えないので要らない |

### 年のサブカタログの名前

**決定**：`y` ＋ 西暦 4 桁（例：`y2024`。collection の ID は `y2024/subcompartments`）。西暦はデータの時点。

**理由**

- 元号（`r6` など）は改元のときに扱いにくい
- 入れ子の collection の ID はルートからのパスになる。Portolan の検証ツール rashid は、パスの区切りごとに `^[a-z][a-z0-9_-]*$` で検査する（ルール PTL-COL-003、仕様 PORTO-CORE-016。SHOULD なので警告）。数字で始まる `2024` は警告になる
- 元データは「令和6年末現在」で、会計年度ではなく暦年末の時点
- ID は URL やスクリプトから参照されるので、公開後は変えない前提で決める

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| `2024` | rashid で警告が出る |
| `as_of_2024` | 意味は読めるが長い |
| `fy2024` | 会計年度ではないので誤解を招く |

### 年ごとのコード表と市町村の表

**決定**：codes と municipalities は、年のサブカタログごとに置く（例：`y2024/codes/`）。その年のデータは、その年の codes・municipalities で読む。

**理由**

- コード表は道が改訂しうる。今の PDF には年や版の記載がない
- 市町村は合併で変わりうる
- 年ごとに置けば、データとコード表の対応が必ず合う。年のサブカタログだけで完結する

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| カタログのルートに 1 つだけ置く | 有効な年を表す列などの工夫が要る |

年が増えると、ほぼ同じ表が年の数だけできるが、codes は 158 行で容量は問題にならない。

### 市町村の表を別のcollectionにする

**決定**：振興局・市町村の表は、codes とは別の collection `municipalities` にし、年のサブカタログの下に並べる。

**理由**

- formats.md（Tabular）では、表データの collection は Parquet を 1 つだけ collection 単位の asset として持つ（single-file collection）のが MUST。codes に 2 つ目の Parquet として置けない
- 元の `森林調査簿コード.xlsx` も、「コード一覧」と「市町村コード」の 2 シートに分かれている

## 4. 列の共通の規則

### 列名

**決定**：列名は元データの見出し（日本語）のまま。振興局によって見出しが違う列は、道の PDF「森林資源データの掲載項目」の名前にそろえる（`支庁コード` → `振興局コード`、`立地距離` → `立地距離コード`）。

**理由**

- 元データや道の資料との対応が明確になる
- 列名や座標系を元データに合わせるという方針を、ほかの決定（コードだけを持つ、JGD2000 にする）とそろえる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 英語のスネークケース（例：`subcompartment_id`）にし、日本語名は `table:columns` に書く | SQL や海外のツールでは書きやすいが、元データとの対応表が要る |

日本語の列名は、SQL で引用符が要ることがあり、古い GDAL のドライバや Shapefile への書き出しで文字化けや切り詰めが起きることがある。

### キーの列名

**決定**：小班のキーは `小班キー`（14 桁）、林班のキーは `林班キー`（10 桁）。

**理由**

- 元データでは同じ値が shp では `キー`、調査簿では `KEYCODE` と別の名前で、林班の shp の `キー` は 10 桁で指すものが違う。何のキーかが列名でわかるようにする
- 結合する表で同じ名前にすれば、DuckDB の `USING (小班キー)` などで結合できる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| `KEYCODE` にそろえる | 林班のキーと区別しにくい |

### コードの値の型

**決定**：コードは固定桁の 0 埋め文字列にする（振興局 2 桁、市町村 2 桁、林班 4 桁、小班 4 桁など）。

**理由**

- 調査簿ではコードが数値で入っていて、先頭の 0 が落ちている。shp では 0 埋めの文字列
- 文字列にそろえると、キーと突き合わせやすく、codes とも結合できる

### 座標系

**決定**：全道のデータは JGD2000 の経緯度（EPSG:4612）にする。元の平面直角座標系は年ごとの `.prj` に従って換算する。

**理由**

- 元データは振興局ごとに平面直角座標系の XI・XII・XIII 系（JGD2000）。GeoParquet の形状の列は 1 つの CRS しか持てないので、全道を 1 ファイルにするには 1 つにそろえる必要がある
- 元データの測地系（JGD2000）にできるだけ合わせる
- 北海道では、PROJ（9.6.2・9.8.1）が選ぶ JGD2000 → JGD2011（EPSG:6698）と JGD2000 → WGS84（EPSG:1826）は、どちらも恒等変換（函館・札幌・旭川・釧路・根室でずれ 0）。国土地理院の測地成果2011 でも、北海道の水平位置は改定されていない。どれを選んでも座標値は同じで、違いは CRS の表記だけなので、元データとの対応が明確なことを優先した
- 平面直角座標での面積と、経緯度からの測地線面積の差は −0.020%〜+0.048%（28,000 件のサンプル）
- Portolan が WGS84 を求めるのは STAC の bbox だけで、データ本体の CRS は自由
- 胆振の元の系は年によって違う。令和5年末は `.prj`・注記のテキスト・座標値がそろって XII 系、令和6年末は `.prj` と座標値が XI 系で注記のテキストだけ 12 系。両年の同じ小班をそれぞれの `.prj` で換算して比べると 93% が対称差 1 m² 以下で一致するので、どちらも `.prj` が正しい

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| JGD2011 の経緯度（EPSG:6668） | 今の国内標準だが、北海道では座標値が同じで、表記を替える利点より元データとの対応を優先した |
| WGS84（EPSG:4326 / OGC:CRS84） | Web 地図の既定に合うが、元データとの関係がわかりにくい |
| 1 つの系（例：XII 系）に寄せる | 系の範囲の外でひずみが大きくなる |
| 系ごとにファイルを分ける | 全道を 1 ファイルにする方針と合わない |
| 元の系番号の列（`source_zone`）を持つ | shp の属性ではなく `.prj` の情報で、振興局と年から決まる。README の表で示す |

### 空欄を0にする列

**決定**：`複層区分コード` と `混植サイン` の空欄は 0 に置き換え、codes に 0 の行（複層区分 0 ＝ 単層林、混植サイン 0 ＝ 混植等ではない）を入れる。ほかの列の空欄は null のまま。

**理由**

- PDF では、どちらも「空欄（0）」で、空欄と 0 が同じ意味
- 複層区分は、単層林の層番号を 0 にするので（[単層林の層番号](#単層林の層番号)）0 の行が要る。混植サインもそろえ、結合すればすべての行に名称が付くようにする
- 調査簿では 0 は使われておらず、すべて空欄

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 混植サインだけ空欄（null）のまま残す | 複層区分とそろわず、結合で名称が付かない行が残る |

### 空欄の意味の書き方

**決定**：空欄の意味は codes に入れず、データ側の列の説明（collection.json の `table:columns`）と README に書く。PDF の定義と、定義がなく推測したもの（例：「欠損と思われる（PDF に定義なし）」）を書き分ける。

**理由**

- core.md（Metadata）は、列の説明を持つことを SHOULD としている
- 表データの collection は Parquet を 1 つしか持てないので、codes に空欄の意味の表を 2 つ目の Parquet として置けない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| codes にコードが null の行を入れる | SQL では null どうしが一致せず、結合で名称が付かない |
| 空欄にコードを割り当てる | PDF にないコードを作ることになる |

## 5. 各 collection の列

### 小班と層を分ける

**決定**：小班の GeoParquet（1 行 1 小班）と、層の Parquet（1 行 1 層、`stand_layers`）を、年のサブカタログの下の別の collection にする。小班の表には、最下層の主な属性も持たせる。

**理由**

- 調査簿の 1 行は小班ではなく「小班 × 層」（複層林は令和6年末で 20,404 小班、最大 4 層）。区画と調査簿は 1 対多
- 分ければ正規化され、面積の二重計上が起きず、どのツールでも扱える
- 形状と属性を別ファイルにする形は formats.md（Tabular）で想定されていて、結合に使う列と結合のコード例を README に書くことが MUST
- QGIS の通常の結合は 1 対 1 で最初の 1 行しか結合せず、PMTiles は小班のファイルから作るので、層の表にしかない属性では色分けできない。最下層の属性を小班の表にも持たせれば、地図の表示や簡単な絞り込みは結合なしでできる
- 国内外の森林データでは、区画と層を別の表にする形が主流で（森林クラウドシステム標準仕様書 Ver.6.1、フィンランド森林センター、BC 州 VRI、長野県、鳥取県、北海道の元データ）、正規化した表に加えて代表の値を持つ区画を配る例も多い（BC 州の `VEG_COMP_LYR_R1_POLY`、フィンランドの WFS 版、鳥取県の小班ポリゴン）

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 小班と層を分けるだけ（代表の属性を持たない） | 地図の色分けに結合が要り、PMTiles で色分けできない |
| GeoParquet を 1 行 1 層にし、形状を層の数だけ複製する | 面積の二重計上、同じ形状の重なり、容量の増加。調べた事例にもなかった |
| GeoParquet に層の配列（list<struct>）の列を持たせる | QGIS・GDAL や PMTiles で入れ子の列を扱いにくい。GIS 向けの配布ファイルの事例もなかった |
| 層を横持ちにする（上層・下層の列を並べる） | 横持ちは層を最大 2 と決めているデータだけで使われている。北海道は最大 4 層 |

### 最下層を代表の層にする

**決定**：小班の表に持たせる代表の層は、単層林はその層、複層林は最下層（`複層区分コード` ＝ 1）にする。

**理由**

- 道の統計（林種・樹種・林相別森林資源構成表、北海道林業統計）と同じ規則にする
- 構成表（令和6年）の面積（林種・樹種・林相・齢級別）は、単層林と複層林の最下層の行で集計した値と一致する（13 振興局で、0 でないセルがすべて 0.006 ha 以内。渡島は林齢を 1 年戻すと一致）
- 最上層の規則では一致しない（例：上川の人工林の面積が 2,421.86 ha 足りない）
- 「人工林の層」を選ぶ規則とも比べたが、最下層が天然林の小班（2 件）で合わなくなる
- 北海道林業統計 下巻 表30 の注 3 には「複層林は上層木を対象としている」とあるが、実データとは合わない。理由はわからない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 最上層（上から見える林冠） | 道の統計と合わない |
| 面積歩合が最大の樹種（林野庁の国有林 GIS、全国森林資源メッシュ） | 北海道の調査簿には層ごとの面積歩合がなく、樹種の比率だけ |
| 業務上の重要度の順位（BC 州） | 北海道の調査簿に該当する値がない |

最下層は樹下植栽された下木であることが多く、地図で上から見える林冠ではないので、README と列名（[最下層の列名](#最下層の列名)）で示す。

### 最下層の属性は名称だけ

**決定**：小班の表の最下層の林種・樹種1 は名称だけを持ち、コードは持たない。名称は codes と同じ表記。

**理由**

- 地図やポップアップで見るには名称が要る。`最下層林種` が名称なら、スタイルの塗り分けもコードを置き換えずに書ける
- コードは、小班キーと `複層区分コード IN ('0', '1')` で層の表と結合すれば取れる（1 小班に必ず 1 行が対応する）。コードを使う分析（年の比較、樹種コードの範囲での絞り込み）は DuckDB などで行うと考える

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| コードと名称の両方を持つ | 結合 1 回で代わりが利く |

### 最下層の列名

**決定**：小班の表の代表の層の列名は `最下層林種`、`最下層樹種1`、`最下層林齢` にする。

**理由**

- 複層林の最下層は林冠とは限らない。地図の利用者は README より列名とポップアップを見るので、最下層の値であることを列名で示す
- 層の表の `林齢` などと名前が重ならない
- 単層林ではその層が最下層でもあるので、意味は正しい

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| `林種`・`樹種1`・`林齢` | 層の表の値か最下層の値かが列名で区別できない |
| `代表林種` など | 最下層の値であることが列名でわからない |

### 導出した値を持たない

**決定**：小班の表に、齢級・林相・蓄積は持たない。道の統計と同じ値の計算のしかたを README と AGENTS.md に書く。

**理由**

- 元の小班の shp にも調査簿にもない値
- 層の表から計算でき、計算した値は道の統計と一致する（齢級：`least(ceil(林齢 / 5), 24)`、蓄積：全層の Σ 面積 × (HA当蓄積N + HA当蓄積L)）
- 林相・蓄積を GIS で使いたい需要は少ないと考えた

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 齢級を持つ（24 齢級で打ち止めにする規則を利用者が知らなくて済む） | 元データにない値。計算のしかたを README に書けば足りる |
| 全層の蓄積を持つ | 同上 |

### 層の数

**決定**：小班の表に `層の数`（その小班の層の行の数。単層林は 1、int8）を持たせる。

**理由**

- 元データにない列だが、複層林かどうか、何層かを結合せずに見られるようにするため
- 調査簿の層は最大 4 層なので int8 に収まる

### 分解した列

**決定**：小班・林班の表に、キーを分解した列（`振興局コード`・`市町村コード`・`枝番`・`林班`・`小班`）を残す。値は shp の列ではなく、キーから切り出して作る。

**理由**

- キーと重複するが、元の shp と調査簿にある列なので残す（元からある属性はできるだけ残す）
- 令和6年末の小班 shp には、分解した列がキーと食い違う地物が 7 件（6 キー）あった。うち 5 キーは、形状と調査簿の面積からキーが正しいとわかった。調査簿の 林班・小班 の列ともキーが一致する
- 林班の飛び地で `枝番` が null の 1 件も、林班キーから `00` になる

### 小班の表に林班キーを持たない

**決定**：`林班キー` は林班の表だけに持たせる。小班から林班へは `left(小班キー, 10)` で結合する。

**理由**

- 小班キーの先頭 10 桁と同じ値で、小班キーと分解した列だけでも内容が重複している。さらに重ねるのは重複が多すぎる
- DuckDB などでは `left(小班キー, 10)` で切り出せる。QGIS では仮想レイヤの SQL（`substr(小班キー, 1, 10)`）で代わりになる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 小班の表にも `林班キー` を持ち、同じ名前の列で結合する | QGIS の通常の結合で使えるが、重複が多すぎる |

### 林班の表の列

**決定**：林班の shp の列をすべて、元の列名で残す（`TEXT`・`RINLBL`・`土保フT` を含む）。`土保フT` は定義がわからないことを README に書く。

**理由**

- 元からある属性はできるだけ残す
- `TEXT` は全道 19,814 件で `林班` と同じ値、`RINLBL` は `林班` の整数と全件一致（ラベル用、先頭の 0 なし）
- `土保フT` は道の資料に定義が見つからない。上川（1,929 林班）で確かめると、`（土保）` の 663 件は、林班の中に保安林（森林の種類 11〜19）の小班がある林班と 597 件が一致し、保安林または砂防指定地（32）に広げると 645 件が一致した。よく重なるが、完全には一致しない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| `TEXT`・`RINLBL` を落とす（`林班` と同じ値なので） | 元からある属性を残す |
| `土保フT` を意味がわかるまで保留する | 元からある属性を残し、わからないことは README に書く |

### 層の表に調査簿の列をすべて置く

**決定**：小班の表と層の表への列の振り分けは、元データのファイルで決める。調査簿の列はすべて、元の順で層の表に置く。小班ごとに決まる値（計画区・面積・森林の種類など）も層の表に置き、層の数だけ繰り返す。層の表の `振興局コード`・`市町村コード`・`林班`・`小班` も残す。

**理由**

- 2 つのファイルが、元データの配り方（shp と調査簿）とそのまま対応する
- 元からある属性はできるだけ残す。調査簿の項目とそのまま対応させる
- 面積を層の行のまま合計すると二重計上になるので、最下層の行に絞って合計することを README に書く。層の行に面積を繰り返す長野県のデータも、利用者案内に同じ注意を書いている

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 値が小班ごとに決まるか層ごとに変わるかで振り分ける（小班ごとの値は小班の表に置く） | 元データのファイルとの対応がわかりにくくなる。小班ごとの値にも数件の例外（面積・森林の種類1・代表地番）がある |

### 単層林の層番号

**決定**：単層林の `複層区分コード` は 0 にする。層の表の一意キーは `小班キー` ＋ `複層区分コード`。

**理由**

- 元データでは単層林の `複層区分コード` が空欄。PDF のコード表では 0 ＝ 単層林
- 一意キーの片方が null にならない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 元データのまま（単層林は null） | 一意キーの片方が null になり、結合や主キーとして扱いにくい |
| 単層林も 1 にする | 「1 ＝ 下木」というコード表の意味と食い違う |

### 繰り返しの列は横持ち

**決定**：`森林の種類1コード`〜`森林の種類6コード` と、`樹種1コード`〜`樹種3コード`・比率は、元のとおり横持ちにする。

**理由**

- 調査簿の列はすべてそのまま層の表に置くため
- 最大数が決まっていて、QGIS・PMTiles でもそのまま扱える

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 別の表に分ける、リスト（配列）の列にする | 元の列との対応がなくなり、扱えるツールが減る |

### 数値の列の型

**決定**：層の表の数値の列は、全道の値が収まるいちばん小さい型にする。

| 列 | 型 | 値の範囲（令和6年末） |
|---|---|---|
| `樹種1比率`〜`樹種3比率` | int8 | 1〜9（混植の層 12,037 行だけに値がある） |
| `林齢`（小班の `最下層林齢` も） | int16 | 1〜320 |
| `HA当蓄積N`・`HA当蓄積L` | int16 | 1〜803 m³/ha（PDF も単位未満四捨五入） |
| `成長率N`・`成長率L` | double | 0.001〜27.239（小数 3 桁まで） |
| `樹高` | int8 | 1〜37 m（PDF も単位未満切り捨て） |
| `面積` | double | 0.01〜414.44 ha（小数 2 桁まで） |

**理由**

- 値の意味（整数か小数か）を型で示し、容量を抑える
- 成長率は定義が道の資料にない。値は割合と思われ、1 を超える行（`成長率N` 4,125 行、`成長率L` 0 行）はいずれも林齢 1〜5 年の若い林なので、異常値ではないと考える

林班の表の `TEXT`（string）と `RINLBL`（int64）は、元の型のまま。

### 代表地番

**決定**：`代表地番` は文字列にする。数値で入っているセル（28 件）は文字列にし、Excel が日付に変えたセル（18 件）は null にする。件数と小班キーを README に書く。

**理由**

- 日付のセルは、「本番-枝番」を Excel が年月と解釈したものと考えられる。年が 4 桁の 3 件は元の文字列がほぼわかるが、残る 15 件は 2 桁か 4 桁か、区切りの記号が何だったかを確かめられない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 推測で元の文字列に戻す | 確かめられない値を作ることになる |
| 年が 4 桁の 3 件だけ戻す | 同じ列の中で扱いが分かれる |

### 渡島の成長後の値

**決定**：令和6年末の渡島の調査簿は、1 年成長させた値（シート名が「成長後」）のまま持ち、統計と林齢・蓄積が 1 年ずれることを README と AGENTS.md に書く。

**理由**

- 加工しない
- 林齢は 1 年戻せるが、蓄積は成長前の値がないので戻せず、不整合が残る

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 林齢を 1 年戻す | 林齢は統計と合うが、蓄積との不整合が残る |

### コード表を別の表にする

**決定**：データ本体（層の表）はコードだけを持ち、名称は持たない。コードと名称の対応は、別の表データの collection（`codes`）にする。

**理由**

- データ本体が元データ（コードだけ）と同じ形になる。列名や座標系を元データに合わせる方針と一貫する
- 名称を 1 か所で管理できる。コード表にない名称が後でわかっても、codes に行を足すだけで済む
- 元のコード表の問題（印刷用の Excel で機械で読めない）は、Parquet にすることで解消する
- コードを残すのは、ほかのデータや年と突き合わせられ、容量もほとんど増えないため

QGIS で名称を見るには、コードの列ごとに結合が要る。層の表の主な利用者は DuckDB や Python で集計する人と考え、許容する。

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| コード列の隣に名称列を持つ | 列が増え、名称が表ごとに散らばる |
| コード列を名称に置き換える | 元データやほかのシステムのコードと突き合わせられない |
| Parquet のフッターのキーバリューに JSON でコード表を入れる | 標準的な読み方がなく、ほとんどのツールが無視する |

### コード表の形

**決定**：codes は、すべての区分を 1 つの縦長の表（区分・コード・名称・略称・針広区分・上位区分・備考）にする。`区分` の値は層の表の列名から番号を除いた名前（例：`樹種1コード` → `樹種コード`）。結合は `区分` ＋ `コード`。

**理由**

- 表データの collection は Parquet を 1 つしか持てないので、区分ごとのファイルにできない
- 区分の名前が列名から決まるので、どの列をどの区分で結合するかがわかりやすい

### コード表に載せる範囲

**決定**：codes には森林簿のコードだけを載せる。計画区・振興局・市町村は載せない。使われていないコードも、PDF にあれば載せる。

**理由**

- 元の `森林調査簿コード.xlsx` が「コード一覧」と「市町村コード」の 2 シートに分かれているのと同じ分け方
- 振興局・市町村は municipalities で扱う

### 名称の表記の正規化

**決定**：codes の `名称`・`略称` は、PDF の印刷用の字間の空白と改行を除き、Unicode の NFKC で正規化する。`備考` は空白を除かず、NFKC だけをかける。municipalities の文字列の列にも NFKC をかける。元の表記は残さず、PDF の URL とハッシュ値を README に書く。

**理由**

- オープンデータとして、表記の揺れは好ましくない。PDF の全角・半角の混在は組版や旧システムの都合で、意味のある区別ではない
- 字間の空白の除去や個別の直しで、PDF の字面をもともと完全には守っていない
- 同じ表の中で列によって表記の規則が違うのは不自然。名称と備考で同じ語の表記もそろう（例：樹種 22 の名称の `F1` と備考の `Ｆ１`）
- `備考` は文で、印刷用の字間を詰める必要がない。樹種 22 の注6 は `（　）`・`〔　〕` の中の空白で「中身が入る場所」を表していて、除くと `()` になって読みにくい
- 立地距離の `～` は NFKC で ASCII の `~` になるが、個別の直しは増やさない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| PDF の表記のまま残す | 表記の揺れが残る |

全角・半角の統一の根拠になる国のルールも探したが、見つからなかった。

### 個別に直した名称

**決定**：NFKC のあと、次の 2 行を個別に直し、備考に理由を書く。

- 森林の種類 55：`地帯区分未定地域内の森林` → `地種区分未定地域内の森林`
- 疎密度 0：`２，１、０` → `2、1、0`（区切りを読点にそろえる）

**理由**

- 森林の種類：PDF では 45 が「地種区分」、55 が「地帯区分」で、zip の中の xlsx は 45・55 とも「地帯区分」だった。道の資料だけでは決め手がないので、国の資料を調べた
  - 林野庁測定規程 付録7「国有林野森林図式」（<https://www.rinya.maff.go.jp/kanto/map/attach/pdf/index-1.pdf>）に、法令等の指定の記号として「国立公園地種区分未定の特別地域」などがある
  - 環境省の国立公園の解説（<https://www.env.go.jp/park/about/history.html>）も「地種区分」を使い、「地帯区分」は使っていない
  - 自然公園法の条文に「地種区分」の語があるかは確かめていない。調査簿では 45・55 とも使われていない
- 疎密度：NFKC では直らない揺れ（カンマと読点の混在）。カンマは立地距離の `1,000m` のような桁区切りにだけ使うことになる
- 疎密度 0 の備考は、PDF の元の表記を引用しない文にする。引用すると、備考にかける NFKC で表記が変わり、元の表記を示す目的に合わないため

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 疎密度の名称を組み立てる（例：`十分率 8`） | PDF にない表記になる |

### 樹種99の針広区分

**決定**：樹種 99（針広混交林）の `針広区分` は PDF のまま空（null）にし、備考に理由を書く。

**理由**

- 99 は樹種ではなく混交林を表すコードで、PDF の区分の欄も空（針葉樹・広葉樹のどちらのくくりにも入らない）
- 名称と略称（N-L）から、混交であることはわかる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| `混交` という値を入れる | PDF にない値になる |

### 林種の上位区分

**決定**：林種の `上位区分` は、PDF の備考欄の左の段（人工林 / 天然林 / 伐採跡地 / 未立木地）にする。右の段（立木地 / 無立木地）は、列の説明と README に書く。

**理由**

- 左の段のほうが細かく、右の段は左の段から決まる。左の段を持てば両方で集計できる
- 「天然林（コード 2・3）の合計」のような集計が `GROUP BY 上位区分` でできる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 右の段（立木地 / 無立木地）にする（疎密度の上位区分とそろう） | 粗く、左の段の集計ができない |
| 上位区分の列を 2 つにする | 2 段のくくりがあるのは林種だけで、ほかの区分では 2 列目が空になる |

### 区分全体の注書き

**決定**：PDF の区分全体にかかる注書きは、codes の列にせず、内容によって置き場所を分ける。

- データの列の意味（立地距離・疎密度・特定保安林区分・指定施業要件の見出しの補足、森林の種類の「6 つまで」）：層の表の列の説明と README
- codes の名称・略称についての注（森林の種類の注1・注2、樹種の注7）：codes の `名称`・`略称` の列の説明と、codes の README

**理由**

- codes に「区分の説明」の列を足すと、同じ文が区分の全行に繰り返される。列の意味の説明は、データ側にも結局要る

### 市町村の表の行と列

**決定**：municipalities は、元のシート「市町村コード」の見出しのまま、旧市町村ごとの行（212 行）を残す。一意キーは `振興局コード` ＋ `市町村コード` ＋ `林班開始番号`。

**理由**

- 元の表の情報を落とさない
- 振興局だけの一覧は、重複を除いて取り出せる
- 合併した市町村は 1 小班に複数の行が対応するので、重複を除いてから結合する方法を README に書く

### 全国地方公共団体コードを持たない

**決定**：全国地方公共団体コード（6 桁）の列は、どの表にも持たない。総務省の一覧と市町村名で突き合わせる方法を README に書く。

**理由**

- 元データにない列
- 北海道の中では市町村名が重複しないので、総務省「全国地方公共団体コード」（<https://www.soumu.go.jp/denshijiti/code.html>）の一覧と市町村名で突き合わせれば、利用者が自分で付けられる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| municipalities に `団体コード` の列を足す（国土数値情報の行政区域や国勢調査と結合しやすい） | 元データにない列。利用者が付けられる |

### 林班開始番号

**決定**：`林班開始番号` は元のまま string（1 文字）で持ち、林班の千の位を表す列として説明する。小班・林班と旧市町村は `left(林班, 1) = 林班開始番号` で結合できる。

**理由**

- 令和5年末の元データでは、キーと `枝番` に「0 ＋ 林班の千の位」が入っていて、その (振興局, 市町村, 枝番) の組 212 通りが、municipalities の (振興局コード, 市町村コード, 林班開始番号) の 212 行と 1 対 1 で一致した
- 元の値は `0`〜`4` で、各市町村の 1 つ目の行が `0`

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| `枝番` に合わせて 2 桁の 0 埋めにする | 元の値を変えることになる。千の位の 1 文字として結合できる |

### 計画区

**決定**：計画区は、層の表に名称の文字列のまま持つ。番号は補わない。codes にも municipalities にも入れない。

**理由**

- 元データ（調査簿）に文字列の列としてあり、調査簿の列はすべて層の表に置く
- 番号は道の資料にない
- 1 つの市町村（179 市町村）は必ず 1 つの計画区に属する。名称は道の地域森林計画のページ（<https://www.pref.hokkaido.lg.jp/sr/srk/81069.html>）の 13 計画区と一致する

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| municipalities に列として移す | 調査簿の列との対応がなくなる |
| codes に番号と名称の行として入れる（森林クラウドの 001〜013） | 番号が道の資料になく、codes は森林簿のコードだけを載せる |

## 6. 形状の処理

### 同じキーの地物を融合する

**決定**：同じキーの地物は融合（union）して 1 行にする。

**理由**

- 小班キーを一意にし、層の表と結合しても行が増えない（蓄積などの二重計上を防ぐ）
- 調べた公的な森林区画データの大半が「1 ID ＝ 1 地物」で、林野庁の国有林 GIS も分かれた小班を MultiPolygon にしている
- 令和6年末の 3,092 小班のうち 3,054 件は部分どうしが離れていて、まとめても形状の情報は失われない
- 部分を束ねるだけだと、辺を共有する・重なる部分を持つ不正な MultiPolygon になる。融合すれば、接している部分（37 件）は境界が消えて 1 つの面になり、重なっている 1 件は重なりが 1 回分になる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 地物ごとの行のままにする | 小班キーが一意にならず、層の表との結合で行が増える |
| 部分を束ねるだけ（融合しない） | 不正な MultiPolygon になる |

### すべてMultiPolygonにする

**決定**：部分が 1 つの形状も含め、すべて MultiPolygon にする（`geometry_types` は `["MultiPolygon"]`）。

**理由**

- Cloud-Native Geospatial の GeoParquet ガイドは、1 列に同じ型だけを入れることを推奨している

### 面にならないリングと不正な形状

**決定**：点が 4 つ未満のリングだけを除き、残りの部分を使う。不正な形状は GEOS の `make_valid` で直す。経緯度に換算したあとにも `make_valid` をかける。直した件数と小班キーを README に書く。

**理由**

- 面にならないリングは面積を持たない線なので、除いても面の情報は失われない
- 不正な形状は、重なりの判定や面積の計算でエラーや不正確な結果になる
- 令和6年末は、元の平面直角座標系では不正な形状が 0 件だったが、経緯度に換算しただけで 7 件が不正になった

### 形状がない小班

**決定**：まとめても形状がない小班は、形状を null にして行を残す（`GIS面積`・`bbox` も null）。

**理由**

- 元データでも、小班の shp のキーと調査簿の KEYCODE は過不足なく一致する。行を除くと、層の表にだけある小班キーができる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 形状がない小班の行を除く | 層の表にだけある小班キーができる |

### GIS面積を計算し直す

**決定**：`GIS面積` は、まとめた形状から、すべての小班で計算し直す。計算は振興局ごとの元の平面直角座標系で行い、小数 4 桁（0.0001 ha ＝ 1 m²）に丸める。列名は `GIS面積` のまま。

**理由**

- 元の値は地物（部分）ごとの面積で、まとめたあとの行（小班全体）の属性としては意味を持たない
- 部分の合計で代用すると、重なっている小班や、同じ値が並ぶ 16 件のように、形状と合わない値が混ざる
- 分かれていない小班も同じ方法で計算し、同じ列に元の値と計算した値が混ざらないようにする
- 元データと同じ座標系で計算すれば、元の値と比べられる。令和6年末の分かれていない小班では、差の絶対値の中央値が 0.0025 ha、0.01 ha 以内が 99.95%
- 元の shp の 0.01 ha 単位に丸めると 0.005 ha 未満の小班が 0 になる。座標の精度（元の shp は mm 単位）から見て、1 m² より細かい桁には意味がない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 部分の GIS面積の合計にする（元の値を残す） | 形状と合わない値が混ざる |
| 0.01 ha に丸める（元と同じ） | 小さい小班が 0 になる |

### 林班の表と結合できない小班

**決定**：令和6年末で林班の表に林班キーが見つからない小班 91 件は、次のように扱う。

| 林班 | 扱い |
|---|---|
| 宗谷 `1004001059`（43 小班） | 林班 shp で 1151 林班の一部として描かれていた区画を、1059 林班として切り出す。`TEXT` は `1059`、`RINLBL` は 1059、`土保フT` は切り出し元と同じ null |
| 胆振 `0412000029`（39 小班）、石狩 `0602000003`（9 小班） | 林班 shp にポリゴンがない。補わず、欠落のままにする |

小班が 1 つもない林班（58 件）は、そのまま残す。

**理由**

- 宗谷：1151 林班の 2 つの部分（12 km 離れている）のうち、1059 の小班 43 件をすべて含み 1053〜1063 林班に接する部分は、1151 の小班を 1 つも含まない。明らかな誤りで、元の形状を付け替えるだけで新しい形状は作らない。全道で `TEXT` ＝ `林班`、`RINLBL` ＝ `林班` の整数という関係が全件成り立つので、それに合わせる
- 胆振・石狩：小班の形状を融合して補うと、道の林班の境界と同じになるとは限らない、元データにない形状を作ることになる。石狩は飛び地か欠落かもわからない
- 小班がない 58 林班：実質的に重なる小班はなく（境界で接する・わずかに重なるだけ）、調査簿にもその林班キーの行がない。小班は林班のうち森林計画の対象になる森林の部分にだけ描かれていて、対象の森林がない林班と推測する

### 林班をまたぐ小班

**決定**：令和6年末の宗谷 `10040001390502` は、キーのとおり 3 地物を 1 行にまとめる。138・139 林班をまたぐ小班になることを README に書く。

**理由**

- 3 地物のうち 2 地物は形状が 138 林班の中にあり、shp の分解した列（138 林班）と合う
- しかし調査簿のこのキーの行の面積 0.7 ha が 3 地物の合計 0.69 ha と合い、138 林班 502 小班（0.04 ha）に移すと合わなくなる
- キーを正とする規則（[分解した列](#分解した列)）とも一致する

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 2 地物を 138 林班 502 小班に移す | 調査簿の面積と合わなくなる |

## 7. GeoParquet・Parquet の書き出し

### 行グループの行数

**決定**：小班・林班の表は 1 行グループ 10,000 行にする。形状のない表は既定の行数。

**理由**

- formats.md（GeoParquet）は、1 行グループ 150,000 行以下を MUST としている
- 行グループを小さくすると、bbox の統計で読み飛ばせる行が増える。全道の小班（令和6年末の試作）で比べた結果は次のとおり（範囲の列は、bbox の統計で読む対象に残った行数）

| 1 行グループの行数 | 行グループの数 | 上川の範囲 | 旭川付近の小さい範囲 | 大きさ |
|---|---:|---:|---:|---:|
| 50,000 | 18 | 530,834 | 180,834 | 218 MB |
| 10,000（採用） | 89 | 240,834 | 30,834 | 212 MB |

- 10,000 行は、geoparquet-io が推奨する範囲（10,000〜200,000）にも入る

### 座標を丸めない

**決定**：経緯度に換算した座標は丸めない。

**理由**

- 小数 8 桁（約 1 mm）に丸めると、不正な形状が小班 127 件・林班 1 件できた（換算しただけでは小班 7 件）
- 丸めによる縮小は、小班 −1.3%（216.1 → 213.3 MB）、林班 −2.9% だけで、効果がほとんどなかった

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 小数 8 桁（約 1 mm）に丸める | 上のとおり |
| 小数 7 桁（約 1 cm）に丸める | 元データ（mm 単位）の精度より粗くなる |

## 8. STAC のメタデータ

### 同期日時とデータの時点

**決定**：`updated` は、元の zip を道のサーバーから取得した時刻にする（令和5年末：`2026-11-06T14:03:59Z`、令和6年末：`2026-11-02T15:08:01Z`）。データの時点（`extent.temporal`）は、年末の日付を 1 点で、その日の 0 時（世界標準時）で表す（例：`2024-12-31T00:00:00Z`）。

**理由**

- Portolan は、mirror が同期するたびに `updated` に記録するとしている
- 道のサーバー上の zip の更新日時は、道がファイルを更新した日で、同期した日ではない
- 時点は日付単位なので、日付の 0 時（世界標準時）で表す一般的な書き方にした

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| `updated` に道のサーバー上の zip の更新日時を使う | 同期した日ではない |
| 時点を日本時間に合わせる（`2024-12-30T15:00:00Z`） | 日付単位の時点の書き方として一般的でない |

### ライセンスと出典

**決定**：すべての collection の `license` は `CC-BY-4.0`。`links` に北海道オープンデータ利用規約へのリンク（`rel: license`）を付ける。README に出典・改変の内容・北海道の公式データではないことを書く。

**理由**

- core.md（License）は、各 collection の `license` に SPDX の識別子を書くことを MUST としている
- 北海道オープンデータ利用規約（<https://www.pref.hokkaido.lg.jp/kz/dxs/opendata/hokkaido_od_kiyaku.html>）は、原則として CC BY 4.0 を適用する。元データのページとコード表 PDF のページには CC-BY のマークがある
- 規約は、出典の表示と、改変したことがわかる記載（「〜を改変して利用しています」など）を求めている。SPDX の識別子だけでは、規約の出典の書き方などが伝わらないので、規約へのリンクも付ける
- 規約は、改変した情報を北海道が作成したかのように公表・利用することを禁じている。mirror の位置づけとも合わせ、公式データではないことを冒頭に書く

### providers

**決定**：各 collection の `providers` は、北海道（`producer`・`licensor`）、公開する個人（`processor`・`host`）の順に書く。連絡先は `url` だけにし、メールアドレスは載せない。

**理由**

- core.md（Providers）は、`producer` を 1 つ以上、`host` をちょうど 1 つ最後の要素として書き、host に連絡先（`url` または `email`）を持つことを MUST としている。`processor`・`licensor` は SHOULD
- 公開する個人は、元データを変換・修正した主体でもあるので `processor` も付ける
- `url` だけで連絡先の MUST を満たす

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 会社を host にする | 個人の検討として公開する |

## 9. PMTiles・スタイル・サムネイル

### PMTilesの範囲と属性

**決定**：小班と林班の collection に PMTiles・既定のスタイル・サムネイルを付ける。表データの collection には付けない。PMTiles には形状と bbox 以外の全列を入れる。

**理由**

- core.md（Visualization）は、地理空間の collection が追加の仕組みなしで描ける方法を持つことを MUST としている。小班の GeoParquet は約 210 MB で、そのままでは描けない。ベクタには PMTiles が推奨されている
- PMTiles を付けるなら、MapLibre GL のスタイル（v8）を `styles/` に置き、既定のスタイルで描いたサムネイルを付けることが MUST
- formats.md（Tabular）で、可視化の派生物は表データには当てはまらないとされている
- 列が少ないので、全列を入れて、地図のポップアップで小班の表の値をすべて見られるようにする

### ズーム

**決定**：小班は 11〜14、林班は 7〜14。

**理由**

- 令和6年末で作って比べた結果は次のとおり

| 小班の範囲 | ファイル | 最大のタイル（圧縮） |
|---|---:|---:|
| 10〜15 | 416 MiB | 975 KiB |
| 10〜14 | 296 MiB | 975 KiB |
| 11〜14（採用） | 256 MiB | 525 KiB |
| 12〜14 | 210 MiB | 183 KiB |

| 林班の範囲 | ファイル | 最大のタイル |
|---|---:|---:|
| 7〜14（採用） | 35.2 MiB | 315 KiB |
| 8〜14 | 34.3 MiB | 203 KiB |
| 8〜15 | 59.8 MiB | 203 KiB |

- 最大ズーム 15 を足すと小班 41%、林班 73% 大きくなるが、14 のタイルを拡大して描けば見た目はほとんど変わらない
- 小班をズーム 10 から入れると 1 タイルが最大約 1 MB になり、表示が重い。ズーム 10（振興局 1 つ分の縮尺）では小班は細かすぎて模様にしか見えず、縮小したときは林班が描かれる
- 林班は、全道を 1 画面に入れたときにも描かれるように 7 からにする。8 からと比べて 1 MB しか増えない

### 色とsourceの名前

**決定**：小班は `最下層林種` で 4 色に塗り分ける（人工林 `#1f8a70`、天然林 `#9ccc65`、伐採跡地 `#e8a33d`、未立木地 `#b0a99f`）。スタイルの source の名前は collection の名前（`subcompartments`・`compartments`）にする。

**理由**

- 色は、確認用の地図で実物を見て決めた
- source の名前を collection の名前にすると、2 つのスタイルを 1 枚の地図に重ねたときに名前がぶつからない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| source の名前を両方 `data` にする | 重ねたときに名前がぶつかる |

### ラベル

**決定**：`林班-小班` のラベルは、林班・小班とも先頭の 0 を除いて表示する（例：`0139`・`0502` → `139-502`）。値そのものは変えない。グリフは MIERUNE/fonts（`https://mierune.github.io/fonts/{fontstack}/{range}.pbf`）の `Noto Sans Regular` から読む。

**理由**

- 道の「森林調査簿コード表」（<https://www.pref.hokkaido.lg.jp/sr/srk/97786.html>）は、林班も小班も「4 桁の算用数字からなる番号」と定めている。小班は 1 つの 4 桁の番号で、上 2 桁と下 2 桁に分かれた意味はない
- 道の林班の shp のラベル用の列 `RINLBL` も、先頭の 0 がない整数（例：林班 `0092` → `92`）
- ラベルは数字と `-` だけなので、英数字の範囲のグリフで足りる。グリフが読めなくても塗りと線は描かれる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 上 2 桁と下 2 桁を分けて表示する | 道の資料では 1 つの番号 |
| グリフをカタログの中に置く | 相対パスの確認が要る |

### スタイルの相対パス

**決定**：スタイルの source の `url` は、`styles/` からの相対パス（例：`pmtiles://../subcompartments.pmtiles`）にする。公開時にも絶対 URL に書き換えない。README に、相対パスを解決してから MapLibre に渡すコード例を書く。

**理由**

- 置き場所を移したり、ミラーを作ったりしても、スタイルを作り直さずに済む
- formats.md と Portolan の参照カタログも相対パス
- MapLibre GL JS（5.24.0、pmtiles 4.5.0 で確認）も pmtiles のプロトコルも、この相対パスをスタイルの URL ではなく、表示しているページの URL を基準に解決する。スタイルの URL をそのまま渡すと描けないが、スタイルを取得して相対パスを絶対 URL に直してから渡すと描ける

引き換えに、スタイルの URL をそのまま貼る使い方（MapLibre の `style` に URL を渡す、Maputnik など）では描けない。

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 公開時に絶対 URL へ書き換える | 誰でも URL をそのまま使えるが、置き場所を変えると作り直しが要り、ミラーを作る人も書き換えが要る |

## 10. 元データに加えた変更

### 融合した小班の一覧

**決定**：令和6年末の融合した 3,092 小班のキーは、小班の README に折りたたみ（`<details>`）で全部載せる。令和5年末の融合（137,524 小班・169 林班）は、件数と理由だけを書き、キーの一覧は載せない。

**理由**

- 個別の小班に関わる変更は、件数とあわせて小班キーも載せる。融合したあとのデータからは、どの小班を融合したか見分けられない
- 令和6年末の融合には、接する部分の境界が消えるなど、形状が変わるものがある
- 令和5年末の融合は、元の shp が離れた部分を別の地物にしていたもので（すべて離れた部分どうし）、形状は変わらない。一覧がなくても利用者は困らない。README に載せると約 2.5 MB になる

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 別の CSV ファイルにする | 仕様の構成にないファイルが増える |
| 小班の表に `元の地物数` の列を足す | 変更の記録のためだけに Parquet と PMTiles を作り直すことになる |
| 件数だけにする（令和6年末も） | 個別の小班の変更はキーを載せるという規則と合わない |

## 11. 利用者向けの説明（README・AGENTS.md）

### 範囲と取扱の注意

**決定**：README の冒頭に、データの範囲（一般民有林だけで、国有林と道有林を含まない）と、元のページの「資料の取扱の注意」を出典つきで載せる。

**理由**

## 12. 年による違い

### 令和5年末のキーの枝番

**決定**：令和5年末のキー（「0 ＋ 林班の千の位」の枝番）は元のまま持つ。年をまたいで結合するときのそろえ方（枝番を `00` にする式）を README に書く。

**理由**

- 元データの値を書き換えない（mirror として変える点を増やさない）
- そろえ方が正しいことを確かめた
  - 規則の例外は 0 件（小班 shp 1,102,283 地物、林班 shp 20,054 地物、調査簿 895,568 行）
  - 枝番を `00` にそろえても衝突は 0 件で、対応は 1 対 1
  - 面積の重なりが最大の相手は、林班は相手がある全件、小班は 99.4〜99.5% で、そろえたキーの区画だった
  - 林班 1000 番台以上（そろえて初めて一致する組）と 999 以下で、形状・林齢・林種・樹種の一致の質に差はない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 枝番を `00` に直す | キーはそのまま一致するが、元のキーを書き換える |
| そろえたキーの列を足す | 年の間で列がずれ、キーの情報が重複する（小班の表に林班キーを持たないのと同じ問題） |

### 令和5年末の代表地番

**決定**：令和5年末の stand_layers は 33 列にし、`代表地番` の列を作らない。年をまたいで読むときは `union_by_name = true` とすることを README に書く。

**理由**

- 令和5年末の調査簿は 33 列で、道の「森林資源データの掲載項目」（令和5年末）も 33 項目。代表地番は載っていない
- 元データにない列を、すべて null の値で作らない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 34 列のまま、`代表地番` をすべて null にする | 年の間で列はそろうが、値のない列が増える |

### 林齢幅コード

**決定**：令和5年末の胆振の調査簿にだけある `林齢幅コード` は持たない。値が入っていた行と、定義が資料にないことを README に書く。

**理由**

- 道の掲載項目の PDF にもコード表にも載っておらず、定義がわからない
- 値（1〜5）は天然林・天然生ぼう芽林の行にだけ、その全行（26,916 行）に入っていて、コードが大きいほど林齢が高い傾向がある。林齢の幅の区分と読めるが推測
- 1 つの振興局の 1 年分にだけある列

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| y2023 の stand_layers の列として持ち、胆振以外は null にする | 定義がわからず、ほかの振興局と年では値のない列になる |

### 令和5年末のshpの列

**決定**：令和5年末の小班・林班の表は、令和6年末と同じ列にする。令和5年末の shp にだけある列は持たず、林班の `土保フT`（令和5年末にはない）は作らない。持たなかった列を README に書く。

**理由**

- 増えた列の多くは、ラベル用（`TEXT`・`SYOLBL`）やシステム内部の値（ラベルの位置、通し番号、定数）
- `旧市町村` は枝番から municipalities で引け、`計画区コー` は層の表に計画区の名称がある。ほかの表から同じ情報が得られる
- 令和5年末の小班 shp は 1 つの小班を部分ごとに別の地物にしている（1,102,283 地物 → 874,938 小班）ので、地物ごとの値は 1 行にまとめると、どの部分の値を残すか決められない
- `UPDATEDATE`・`EDITFACTOR` はほかから得られない編集の記録だが、値があるのは 37 地物だけで、地物ごとの値。README に件数を書くにとどめる
- `土保フT` をすべて null で作らないのは、[令和5年末の代表地番](#令和5年末の代表地番)と同じ考え方

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 内部の値でない列（`旧市町村`・`計画区コー` など）だけ足す | ほかの表から同じ情報が得られる |
| 元の shp の列をすべて持つ | 地物ごとの値を 1 行にまとめられない |

### 令和5年末のコード表

**決定**：令和5年末の codes は、令和6年末と同じ「森林調査簿コード表」PDF から作る（中身は同じ）。

**理由**

- 令和5年末のページには、コード表へのリンクがない
- zip の中のコード xlsx（抜粋）は 2 つの版がある（渡島だけ令和6年末と同じ版、ほかの 13 振興局は疎密度・立地距離・傾斜などの区分を足した版。足された区分の名称は PDF と同じ）
- PDF は全区分がそろったいちばん完全な資料で、令和5年末の調査簿で使われているコードもすべて載っている
- codes を年ごとに置く理由（改訂の可能性）に当たる違いは、令和5年末と令和6年末の間で見つかっていない

**検討したほかの案**

| 案 | 採らなかった理由 |
|---|---|
| 令和5年末の zip の中の xlsx から作る | 抜粋で、版が 2 つあり、全区分がそろっているかわからない |
